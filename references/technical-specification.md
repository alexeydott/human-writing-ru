# Нормализация и редактура технических заданий

Этот reference используется для ТЗ, спецификаций требований, SRS-подобных документов, конкурсных/проектных требований и backlog-документов, когда требуется привести текст в порядок **без изменения согласованного смысла**.

## Основной принцип

Редактура ТЗ — это не литературное улучшение. Приоритет: сохранить обязательность, ограничения, числа, единицы, роли, условия, исключения, интерфейсы, ссылки, термины и критерии приёмки. Красивый текст вторичен.

Перед глубокой правкой сформируй инвентаризацию требований: `ID → субъект → обязанность → объект → условие → ограничение/метрика → способ проверки → источник/зависимость`. Если элемента нет, не выдумывай его.

## Режимы

1. **normalize-safe** — только безопасная техническая нормализация: пробелы, одинаковые маркеры списков, очевидные опечатки, единообразие уже выбранных терминов. Смысл не меняется.
2. **edit-requirements** — улучшение формулировок требований. Каждая смысловая правка должна быть проверена на сохранность модальности и фактов.
3. **restructure** — перестройка разделов и группировка требований. Не объединяй требования только ради компактности.
4. **gost34** — структура по ГОСТ 34.602-2020 для АС.
5. **gost19** — структура по ГОСТ 19.201-78 для программы/программного изделия.

Профили `gost34` и `gost19` не включай автоматически: соответствие стандарту — отдельное требование пользователя/проекта.

## Как улучшать отдельное требование

Рабочая форма, когда она уместна:

`<Субъект> должен <действие> <объект> [при <условии>] [с <ограничением/метрикой>].`

Затем отдельно — критерий/метод проверки. Не вставляй в каждую строку искусственное «Система должна», если субъект уже однозначен на уровне таблицы или раздела.

Проверяй единичность/атомарность, однозначность, проверяемость, выполнимость, непротиворечивость, необходимость и трассируемость. ГОСТ 34.602-2020 прямо перечисляет единичность, непротиворечивость, актуальность, выполнимость, проверяемость и однозначность. ISO/IEC/IEEE 29148:2018 посвящён requirements engineering и характеристикам хороших требований.

## Неопределённые слова

Не запрещай слова механически. В обязательном требовании отметь для проверки оценочные формулировки вроде «быстро», «удобно», «современно», «качественно», «интуитивно понятно», «оптимально», «в кратчайшие сроки», «своевременно», если в контексте нет наблюдаемого критерия.

Нельзя автоматически заменять «быстро» на «не более 2 секунд»: это выдумка. Правильная редакторская реакция — пометить параметр как требующий определения.

## Модальность

Сохраняй различие между обязательностью, запретом, разрешённой возможностью, рекомендацией и неопределённостью. Опасны сочетания «должен по возможности», «должен желательно», «обязательно при необходимости»: они часто смешивают уровни обязательности. Не исправляй их без понимания бизнес-смысла.

## Атомарность

Не дели предложение только из-за союза «и»: единое действие может иметь составной объект. Делить стоит, когда части можно независимо реализовать, проверить, приоритизировать или изменить.

## Проверяемость и приёмка

Для функциональных требований достаточно однозначного наблюдаемого результата; число требуется не всегда. Для нефункциональных требований чаще нужны метрика, границы, нагрузочный профиль, среда и метод измерения. Критерий приёмки не должен повторять требование другими словами: он описывает проверку и ожидаемый результат.

## Терминология

Создай канонический словарь терминов. Один объект — одно основное имя. Не переименовывай API, поля, роли, статусы, внешние системы и юридические названия ради стилистики.

## Структура

Для обычного проектного ТЗ структура определяется договорённостями проекта. Не объявляй отсутствие ГОСТ-раздела ошибкой в профиле `generic`.

Для `gost34` структурный checker проверяет наличие разделов ГОСТ 34.602-2020. Для `gost19` — разделов ГОСТ 19.201-78. Он проверяет заголовки эвристически и не заменяет экспертную проверку содержания/оформления.

## Порядок безопасной переработки

1. Зафиксируй исходник.
2. Запусти `check_tz_ru.py` и общий `check_prose_ru.py --mode technical`.
3. Составь карту требований и открытых вопросов.
4. Выполни редактуру, не добавляя фактов.
5. Запусти `check_edit_integrity.py source edited`.
6. Повторно запусти `check_tz_ru.py`.
7. Ручная проверка всех warning, чисел, модальности, отрицаний, условий и внешних ссылок.

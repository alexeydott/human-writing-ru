# Сетевой запуск — протокол принятия решения v3

Для реального получения внешних данных используется рабочий конвейер GitHub Actions `.github/workflows/heldout-gate.yml` или обычная машина с Python 3.10+ и исходящим HTTPS.

## Единый рабочий конвейер

```bash
python3 -m pip install datasets PyYAML pypdf
python3 scripts/fetch_local_heldout_corpora.py
python3 scripts/run_local_heldout_workflow.py
```

Загрузчик сохраняет исходные архивы, PDF и подготовленные деревья с сопроводительными
манифестами в `./data`. Каталог целиком локальный: он игнорируется Git и исключён из
сборщика релиза. Исполнитель
автоматически находит `data/<source_id>/manifest.csv`; альтернативный корень можно
передать через `--local-corpus-root` или `HUMAN_WRITING_RU_DATA_DIR`.
Для запросов к GitHub API локальная оболочка использует `GITHUB_TOKEN`/`GH_TOKEN`, а при
их отсутствии — учётные данные активной сессии `gh auth`. Токен передаётся только на
`api.github.com`; GitHub Actions использует `${{ github.token }}` с `contents: read`.

Эквивалентный низкоуровневый запуск:

```bash
python3 scripts/run_external_heldout_gate.py \
  --output-dir data/heldout-work \
  --local-corpus-root data
```

`taiga_social`, `duma_speeches_1994_2021` и `pravo_open_data` входят в набор источников
по умолчанию как необходимые слои для текущих проверок разнообразия и provenance
профилей `prose`/`oral`/`official`. Если локальные деревья не найдены, получение
продолжится как диагностический запуск, но полная проверка доказательств v3 ожидаемо
останется недостижимой. Исходные сторонние корпуса не следует помещать в публичный
релиз только ради CI.

Исполнитель выполняет строго:

1. проверку SHA зафиксированных входов политики;
2. получение источников независимо друг от друга;
3. устранение дублей/проверку и создание `manifest.validated.csv`;
4. проверку размера всех пяти профилей;
5. **только после него** запуск `scripts/ablate_signals_v3.py`;
6. проверку v3: разнообразие профилей, пригодность/разнообразие сигналов и связанный калибровочный/проверочный split;
7. создание `alert-adjudication.csv`;
8. повторный запуск с `--annotations` после разметки естественных срабатываний;
9. повторную проверку зафиксированных хешей.

Исторический `scripts/ablate_signals.py` сохраняется для воспроизведения 1.4, но текущий сетевой исполнитель не вызывает его для новых решений.

## Новый рабочий каталог и продолжение

По умолчанию координатор начинает **новый запуск**: удаляет прежние созданные манифесты,
отчёты и результаты решения и не наследует старые строки `manifest.csv`. Исходные файлы
могут физически оставаться в рабочем каталоге, но в новый вход решения попадают только
строки текущего получения.

Продолжение предыдущего получения разрешается только явно через `--resume`. Существующий
манифест при этом должен содержать только ID источников из текущего `--sources`; иначе
исполнитель останавливается до проверки контрольного набора. Это защищает проверку от незаметного
смешивания разных экспериментов.

## Происхождение локального корпуса

Для локальных корпусов естественные границы и проверенные поля `speaker`/`author` лучше передавать файлом `<local-root>/manifest.csv`. Минимальное поле — `path`; поддерживаются `id`, `author_or_group`, `split_group`, `source_document_id`, `independence_group`, `channel`. Путь обязан оставаться внутри корня корпуса, ID должны быть уникальны, а `channel` — объявлен для источника в реестре.

Если сопроводительный манифест отсутствует, запасной режим остаётся консервативным: **один `.txt` = один естественный документ**, без выдумывания автора. Например, публичный RUB TSV содержит дату/URL/text, но не отдельное поле `speaker`, поэтому говорящего нельзя восстанавливать эвристически из URL.

Источники со статусом `format_unverified` не допускаются в текущий запуск решения. Их можно исследовать средством получения только через явное исследовательское переопределение; сетевой координатор решений такое переопределение не использует.

## Состояния завершения

- `3` — один или несколько профилей не прошли 50 независимых документов / 10 000 слов; создаётся `DECISION_NOT_RUN.json`;
- `6` — проверка размера пройдена, но доказательств разнообразия/сигналов/split v3 недостаточно; создаётся `DECISION_NOT_READY.json`;
- `7` — проверки доказательств пройдены, но ещё требуется разметка естественных срабатываний;
- `0` — все требуемые этапы доказательств/разметки завершены; это **не** разрешение автоматически менять `editorial-baseline.json`, а только вход для явной проверки политики;
- другие ненулевые коды — ошибки целостности или дочернего процесса.

Основной результат решения — `ABLATION_DECISION_V3.json`. Даже `ready_for_decision_evaluation=true` означает достаточность заранее зарегистрированных проверок доказательств, а не доказанную языковую норму.
